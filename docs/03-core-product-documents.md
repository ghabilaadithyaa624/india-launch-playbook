# 03 · Create the core product documents

Documents are not bureaucracy. They are the cheapest place to find disagreement before development makes it expensive.

| Document | Minimum contents | Owner |
|---|---|---|
| Business brief | Customer, offer, business goal, exclusions, budget | Founder / client |
| PRD | Problem, users, scope, success metrics, non-goals | Product lead |
| User stories | User, goal, acceptance checks, priority | Product + engineering |
| Information architecture | Pages, navigation, content hierarchy | UX / content |
| Wireframes | Key screens and states, not visual polish | UX |
| Design system | Type, colour, spacing, components, accessibility | Designer |
| Data map | Data collected, purpose, location, retention, access | Product + legal |
| Architecture note | Services, integrations, environments, risks | Engineering |
| API contract | Endpoints, auth, examples, errors, versioning | Engineering |
| Launch plan | Owners, dates, dependencies, rollback and comms | Project lead |

## Definition of done

For every user story, write observable completion conditions.

**Example:** "A verified supplier can accept an available request; the requester receives a timestamped confirmation; both parties can see the current state; an operator can resolve a dispute."

Avoid "works well" or "easy to use."
